# 회원 탈퇴 및 개인정보 삭제 설계

## 목표

로그인한 일반 사용자가 보관함에서 직접 탈퇴할 수 있게 한다. 탈퇴 요청이 수락되는 순간 계정의 서비스 접근을 차단하고, 분석 결과와 공유 링크를 즉시 무효화·영구 삭제한다. 결제·환불 대응에 필요한 주문 원장은 구매자를 다시 식별할 수 없도록 비식별화한 뒤 보존한다.

## 사용자 경험

- 보관함 하단에 `계정 관리` 위험 영역과 `탈퇴하기` 버튼을 둔다.
- 확인 모달은 삭제 범위를 명시하고 사용자가 `탈퇴`를 직접 입력해야 제출할 수 있다.
- 제출 중에는 중복 요청을 막는다.
- 성공하면 로컬 세션을 제거하고 랜딩으로 이동하며 재접근을 차단한다.
- 운영자·내부 계정은 이 셀프서비스 경로에서 탈퇴할 수 없다.

## 삭제 정책

### 즉시 삭제 또는 무효화

- V1/V2 분석 결과, 후보 상세, 댓글·프로필 등 결과를 재구성할 수 있는 데이터
- 분석 요청에 저장된 인스타그램 대상 식별 정보와 공유 토큰
- 공유 활성화 상태 및 공유 링크 관측 데이터
- 결과 이미지 객체와 매니페스트. R2 객체가 먼저 삭제된 것이 확인된 뒤 데이터베이스 레지스트리를 정리한다.
- `public.users`의 이메일, 이름, 프로필 이미지, 인증 제공자 메타데이터 등 개인 식별 정보
- Auth 사용자와 활성 세션

### 비식별 보존

- 주문 금액, 상품·플랜, 주문 상태, 결제·환불 처리 상태, 결제 사업자 주문/결제 식별자, 생성·완료 시각
- 회계·중복 결제 방지·환불 감사에 필요한 최소 운영 원장
- 내부 참조 무결성을 위한 불투명 UUID와 `retired` tombstone. 이는 이메일·이름·분석 대상·공유 토큰과 연결되지 않는다.

구매자 이메일·전화번호·표시 이름, 분석 대상, preflight/result 링크 및 재식별 가능한 스냅샷은 주문 원장에서 제거한다. `payment_pending` 상태는 탈퇴만을 근거로 임의 변경하지 않는다.

## 처리 구조

### 1. 서버 엔드포인트

`POST /api/account/delete`를 추가한다.

- 서버의 `getUser()`로 요청자를 확정하고 요청 본문의 사용자 ID는 받지 않는다.
- 동일 출처 검사와 `탈퇴` 확인 문자열을 요구한다.
- 활성 계정이며 일반 외부 사용자일 때만 허용한다.
- 동일 사용자의 중복 요청은 같은 완료 결과를 반환하는 멱등 동작으로 만든다.

### 2. 즉시 접근 차단

트랜잭션 시작 시 account classification을 `retired`로 전환한다. 기존 `requireActiveAccountSession` 경계가 이후 요청을 거부하므로 이미 발급된 JWT가 만료되기 전에도 서비스 데이터에 접근할 수 없다.

### 3. 삭제 상태 기계

`account_deletion_jobs`에 사용자별 단일 작업을 기록한다.

1. `requested`: 탈퇴 요청 접수와 계정 잠금
2. `purging_objects`: 해당 사용자의 R2 결과 이미지 삭제
3. `purging_database`: 분석·공유 데이터 삭제와 주문 원장 비식별화
4. `deleting_auth`: Supabase Admin API로 Auth 사용자 삭제
5. `completed`: 재시도 불필요

외부 객체 삭제는 DB 트랜잭션에 포함할 수 없으므로 durable job으로 처리한다. 사용자에게 성공을 반환하기 전 R2 삭제, DB 삭제, Auth 삭제가 모두 확인되어야 한다. 중간 실패 시 계정은 계속 잠긴 채 동일 작업을 안전하게 재시도한다.

### 4. 데이터베이스 경계

- 새 migration은 `supabase migration new`로 생성한다.
- 탈퇴용 함수는 `SECURITY DEFINER`, 빈 `search_path`, 완전 수식 이름을 사용한다.
- 실행 권한은 `service_role`에만 부여하며 `PUBLIC`, `anon`, `authenticated`에서는 회수한다.
- 함수가 잠금·삭제·비식별화할 모든 행을 사용자 소유권에서 역추적하고, 다른 사용자의 데이터에는 영향이 없음을 PostgreSQL 통합 테스트로 증명한다.
- 주문·revenue ledger의 FK 때문에 `public.users` 행은 물리 삭제하지 않고 비식별 tombstone으로 보존한다.

## 실패 및 경합 처리

- 분석 실행 중 탈퇴하면 먼저 `retired`로 잠가 신규 단계 진입을 막고, 실행 중인 작업은 취소/격리 fence를 통과한 뒤 결과를 삭제한다.
- 결제 webhook과 탈퇴가 경합하면 주문 원장의 결제 상태 갱신은 계속 허용하되 구매자 PII가 다시 채워지지 않게 한다.
- R2 삭제 실패, Auth Admin API 실패, 네트워크 타임아웃은 작업 상태와 제한된 오류 코드만 기록하고 PII나 토큰은 로그에 남기지 않는다.
- 공유 URL은 계정 잠금 직후부터 404로 응답하며, DB 정리 완료 시 토큰 자체도 제거한다.

## 관측성과 개인정보

- 탈퇴 시작·완료·실패 단계와 소요 시간만 구조화 로그로 남긴다.
- 사용자 UUID, 이메일, 공유 토큰, 인스타그램 계정명은 Amplitude·Axiom·Sentry 이벤트에 기록하지 않는다.
- 제품 분석 이벤트는 `account_deletion_started`, `account_deletion_completed`, `account_deletion_failed`의 집계 가능한 결과만 전송한다.

## 테스트 및 출시

- API: 인증 없음, 잘못된 확인 문자열, 내부 계정, 중복 요청, 부분 실패 재시도
- DB: 다른 사용자 격리, 분석/공유 완전 삭제, 주문 PII 제거와 원장 보존, `payment_pending` 불변, 권한/함수 보안
- 객체 저장소: 사용자 소유 R2 키만 삭제되고 실패가 재시도되는지 검증
- UI: 확인 입력 전 비활성화, 제출 중 중복 방지, 성공 후 로그아웃
- 배포는 migration-first로 진행하고 정확한 migration allowlist와 dry-run을 검증한 뒤 앱을 배포한다.
