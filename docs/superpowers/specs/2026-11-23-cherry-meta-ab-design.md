# 체리 사전예약 메타 광고 A/B 테스트 설계 (남친 vs 짝남)

작성일: 2026-11-23 · 상태: 사용자 승인 (2026-11-23, §7의 답변 반영)

## 1. 목적

체리(남친 맞팔 알리미) 사전예약 페이지로 메타 광고를 돌려, 두 니즈 중 어느 쪽이 **실제 결제**로 더 이어지는지 검증한다.

- **가설 A (bf):** 남자친구가 있는 여성은 남친의 새 맞팔을 추적하고 싶다.
- **가설 B (crush):** 남자친구가 없는 여성은 짝사랑하는 남자(짝남)의 새 맞팔을 추적하고 싶다.

같은 타겟에게 메시지만 바꿔 보여주고, 변형별로 광고 → 예약 → 12/1 결제까지 이어서 비교한다.

## 2. 목표 / 비목표 / 실패 조건

**목표**
- 메타 광고 이미지 시안: 같은 그림에 카피만 다른 A/B 쌍.
- 광고 링크의 변형 값(`v=bf|crush`)이 예약 행, Amplitude 이벤트, 메타 픽셀까지 남아서, 12/1 이후 변형별 결제율을 뽑을 수 있다.
- `v=crush`로 들어온 방문자는 '짝남' 문구로 된 랜딩을 본다(광고와 페이지 메시지 일치).
- 메타 A/B 테스트 세팅 가이드와 결제 분석 쿼리.

**비목표**
- 12/1 이후 화면(`/cherry/start`, 결제, 알림톡 문구)의 변형 대응. 현재 '남친' 문구 그대로 둔다(§9 후속 과제).
- 메타 전환 API(CAPI, 서버 전송). 이번에는 브라우저 픽셀만 쓴다.
- 광고 소재 단위(크리에이티브별) 결제 추적. 소재 단위 비교는 메타 픽셀의 예약(Lead)까지만 한다.
- 남친 변형(기본) 랜딩 문구 변경.

**실패 조건 (작동해도 실패로 본다)**
- 짝남 변형에서 '남친' 문구가 잠깐이라도 보이는 깜빡임.
- 광고 없이 들어온 일반 방문자가 bf로 집계되어 A 숫자가 부풀려지는 것.
- 예약 폼에 입력한 이메일·휴대폰 번호가 메타나 Amplitude로 전송되는 것.
- 변형 기록 때문에 예약이 실패하는 것(추적은 항상 부가 기능이다).

## 3. 제약

- 사전예약 마감은 **11/30 자정**(`public/cherry/campaign.mjs`). 광고는 11/24~11/30 약 7일이다.
- 사전예약에서는 결제하지 않는다. 결제는 12/1 이후이고, 예약자는 휴대폰 번호·이메일 매칭(`cherry_reservation_hash_for`)으로 4,900원 혜택을 받는다. 판매 스위치는 아직 꺼져 있다.
- 메타 정책
  - 만 18세 미만은 성별·관심사 타겟을 걸 수 없다. 그래서 **만 18~25세 여성**으로 잡는다.
  - 인스타그램 로고와 화면 모방은 반려 위험이 있으니 시안에 쓰지 않는다.
- 랜딩 카피와 개인정보처리방침 변경은 사용자 확인이 필요하다(§7).
- 프로덕션 DB 변경은 AGENTS.md "Supabase 운영 규칙"을 따른다(격리 workdir, dry-run, allowlist, 적용 후 history 검증).
- 로컬 디스크 여유 약 7GB. 큰 빌드와 브라우저 설치는 피한다(시안 렌더는 설치된 Chrome headless 사용).

## 4. 접근 방식 (짝남 랜딩을 띄우는 방법)

| 안 | 내용 | 장단점 |
|---|---|---|
| **① 서버 문구 교체 (선택)** | `/cherry` route가 `?v=` 값을 읽고 landing.html에 교체표를 적용해 응답 | 깜빡임이 없다. 원본 HTML은 한 벌이다. 픽셀 ID·`data-variant` 주입도 같은 곳에서 한다. 대신 정적 응답이 동적 응답으로 바뀐다. 메타 광고 클릭은 매번 다른 `fbclid`가 붙어 CDN 캐시를 거의 못 타지만, 파일을 메모리에 한 번 읽어 두고 문자열만 바꾸는 처리라 비용은 작다. |
| ② 짝남 파일 별도 생성 | 빌드 때 `landing-crush.html`을 만들어 `/cherry/crush`로 응답 | 완전 정적이다. 대신 빌드 스크립트와 경로가 늘고, `/cherry/*` 하위 앱 경로와 섞인다. |
| ③ 브라우저 JS 교체 | 페이지가 뜬 뒤 문구를 교체 | 가장 간단하다. 대신 깜빡임이 생겨 실패 조건에 걸린다. |

사용자는 결과 중심으로 요청했기 때문에, 구현 방식은 Claude가 ①로 정했다.

## 5. 설계

### 5.1 광고 링크 규칙

```
https://yeosachin.com/cherry?v=bf&utm_source=meta&utm_medium=paid_social&utm_campaign=cherry_ab_1124&utm_content=<소재ID>
https://yeosachin.com/cherry?v=crush&utm_source=meta&utm_medium=paid_social&utm_campaign=cherry_ab_1124&utm_content=<소재ID>
```

- `v` 값은 `bf` 또는 `crush`만 인정한다. 값이 없거나 다른 값이면 변형 없음(null)으로 처리하고 남친 문구를 보여준다. 일반 방문자가 bf로 섞이지 않게 하기 위해서다.
- `utm_*` 값은 메타 보고서와 사람이 읽는 용도다. 서버·DB에는 저장하지 않는다.

### 5.2 랜딩 변형 (`app/cherry/route.ts`)

- `force-static`을 제거하고 `request.nextUrl.searchParams.get('v')`를 읽는다.
- 응답 HTML에 적용하는 것
  - `<html lang="ko">`에 `data-variant="bf|crush"`를 단다(유효한 값일 때만).
  - `crush`이면 §6의 교체표를 적용한다.
  - 메타 픽셀 기본 코드를 `<head>`에 넣는다. 서버 환경변수 `CHERRY_META_PIXEL_ID`(숫자만)가 있을 때만 넣고, 없으면 픽셀 없이 지금과 동일하게 응답한다.
- 캐시: `Cache-Control: public, s-maxage=300, stale-while-revalidate=3600`. landing.html은 모듈 범위에서 한 번만 읽는다(광고 클릭은 `fbclid` 때문에 대부분 캐시를 못 타므로).
- **3D 장면:** `design/namchin-demand/three/hero.js`·`trust.js`는 캔버스에 '남친 팔로잉', '남자친구', '남친은 모르게'를 직접 그린다. 이 소스가 `document.documentElement.dataset.variant`를 읽어 crush 문구(§6)를 그리게 바꾸고, `node design/namchin-demand/build-3d.mjs`로 `public/cherry/3d/`를 다시 빌드한다. 테스트는 3D 소스의 문구 표도 확인한다.
- 교체표는 코드 상수(정확한 문자열 쌍)로 둔다. 테스트로 다음을 확인한다.
  - 모든 원문 문자열이 landing.html에 실제로 있다(원본이 바뀌면 테스트가 실패해 어긋남을 잡는다).
  - crush 출력에 '남친/남자친구'가 허용 위치(FAQ 답변의 대상 목록) 외에는 남지 않는다.

### 5.3 추적

**DB:** `namchin_launch_reservations`에 `variant text null check (variant in ('bf','crush'))` 컬럼을 추가한다.
- 기존 행은 null이다.
- 기존 table-level `grant select, insert ... to service_role`로 새 컬럼도 덮인다.
- 중복 예약(23505)은 지금처럼 원래 행과 변형을 유지한다.

**예약 API (`app/api/namchin/reservations/route.ts`, 페이지는 `/api/cherry/reservations` 재수출 경로로 호출):** 스키마에 `variant: z.enum(['bf','crush']).optional()`을 추가하고 insert에 넣는다. 컬럼이 아직 없다는 오류(PostgREST `PGRST204` 또는 Postgres `42703`)가 나면 variant 없이 한 번 다시 넣는다. 그래서 배포와 마이그레이션 순서가 어긋나도 예약은 절대 실패하지 않는다(실패 조건 4).

**landing.js**
- `document.documentElement.dataset.variant`가 있으면 예약 POST body에 `variant`를 넣는다.
- 예약 완료 시 `window.fbq`가 있으면 `fbq('track', 'Lead', { content_name: variant ?? 'none' })`를 호출한다. 이메일·번호는 보내지 않는다.
- 메타의 '자동 고급 매칭'은 페이지의 이메일·전화 입력칸을 스스로 읽어 갈 수 있다. 그래서 두 겹으로 막는다.
  - 코드: `init` 전에 `fbq('set', 'autoConfig', false, PIXEL_ID)`를 호출한다.
  - 이벤트 관리자: 사용자가 '자동 고급 매칭'을 끈다(새 픽셀은 기본이 켜짐).
  - 배포 후 브라우저로 픽셀 요청에 `ud[` 매개변수가 없는지 확인한다.

**Amplitude (`lib/services/analytics.ts`, `lib/services/cherry-analytics.ts`)**
- `PropertyName`에 `variant`를 추가한다.
- validator는 `enumValidator(['bf','crush'])`로 하고, 체리 이벤트 4종의 스키마에 `['variant']`를 허용한다.
- cherry-analytics.ts는 `data-variant`를 읽어 4개 이벤트 모두에 붙인다(없으면 생략).

**메타 픽셀:** 서버가 넣는 기본 코드가 `init` + `PageView`를 실행한다. 예약 완료 시 `Lead`를 기록한다. 픽셀 ID는 사용자가 메타 이벤트 관리자에서 발급해 Vercel 환경변수에 넣는다.

**운영 콘솔 (`/api/admin/namchin/reservations`, `namchin-waitlist-console.tsx`):** 목록에 변형 열을 추가하고, 상단에 변형별 합계(bf / crush / 없음)를 보여준다.

### 5.4 결제 분석 (판매 오픈 이후)

**결제자 정의(사용자 확정):** 예약자와 매칭되는 계정이 판정 기간 안에 체리를 처음 결제한 경우.
- 매칭 규칙은 `cherry_reservation_hash_for`와 같다. 휴대폰 번호(`users.phone_number_normalized`)가 우선이고, 없으면 이메일로 맞춘다.
- 결제는 `cherry_subscriptions.first_paid_at`이 판정 기간 안에 있는 행이다. 단 `payment_provider = 'grant'`(무상 지급)는 제외한다.
- 4,900원 예약가뿐 아니라 9,900원 정가로 결제한 예약자도 포함한다. `cherry_reservation_claims`만 세면 정가 결제자가 빠지기 때문이다.

**판정 기간(사용자 확정):** 실제 판매 스위치를 켠 시각부터 7일. 판매 오픈 전 예산 대기(`capacity_wait`) 등 변형과 무관한 차단은 두 변형에 똑같이 적용되므로 비교에는 영향이 없다.

**표본이 작을 때:** 변형별 결제자가 30명 미만이면 결제율 차이는 참고용으로만 본다. 판정은 예약 1건당 비용과 '예약 → 결제' 비율의 방향으로 내린다.

빌더는 위 정의로 쿼리를 작성해 가이드 문서에 넣는다.

### 5.5 메타 실험 세팅 (가이드 문서로 제공)

- **캠페인:** 목표는 '잠재 고객'(전환 위치: 웹사이트, 이벤트: Lead). 픽셀 이벤트가 확인되기 전이면 '랜딩 페이지 조회'로 시작한다.
- **A/B 테스트:** 광고 세트 A(bf 소재 4개)와 B(crush 소재 4개)를 만들고, 메타 'A/B 테스트'에서 변수로 '크리에이티브'를 고른다. 두 세트는 예산, 타겟, 지면, 기간이 동일하다.
- **타겟:** 대한민국, 여성, 만 18~25세. Advantage+ 타겟 확장은 끈다. 관계 상태 타겟은 쓰지 않는다(같은 사람들에게 메시지만 달리 보여주는 것이 실험 설계다).
- **지면:** 인스타그램 피드, 스토리, 릴스, 탐색 탭(수동). 4:5는 피드·탐색에, 9:16은 스토리·릴스에 쓴다.
- **기간:** 11/24 ~ 11/30 23:59. 예산은 메타 A/B 화면의 '검정력' 추정이 80% 이상 되도록 잡는다.
- **판정**
  - 진행 중 지표: 변형별 예약 1건당 비용(메타 Lead + DB 변형별 합계로 교차 확인)
  - 최종 지표: 변형별 **결제 1건당 광고비** = 변형 광고비 ÷ 변형 결제자 수(12/1 이후 §5.4)

### 5.6 광고 이미지 시안

- **제작:** HTML/CSS로 그린 뒤 설치된 Google Chrome headless로 PNG를 렌더한다.
  - 자산: Paperlogy·Barlow Condensed 폰트, 체리 색상 토큰, 체리 캐릭터 원본 `design/namchin-demand/og/cherry.png`(1200px 투명), 랜딩 예시 프로필 사진(seoa/rina/maru)
- **크기:** 4:5 1080×1350, 9:16 1080×1920. 9:16은 위 250px·아래 340px에 글자를 두지 않는다.
- **구성:** 컨셉 4 × 변형 2 × 크기 2 = 16장. 같은 컨셉의 A/B는 레이아웃, 사진, 색, CTA가 같고 대상 단어와 그에 딸린 표현만 다르다.

| 컨셉 | A (bf) | B (crush) |
|---|---|---|
| C1 질문 헤드라인 | 내 남친은 나 몰래 / 어떤 여자랑 맞팔하고 다닐까? | 내 짝남은 내가 모르는 사이 / 어떤 여자랑 맞팔하고 다닐까? |
| C2 카톡 알림 목업 | 남친이 맞팔하자마자 / 카톡으로 알려드려요 | 짝남이 맞팔하자마자 / 카톡으로 알려드려요 |
| C3 팔로잉 +1 리빌 | 남친 팔로잉 231 → 232 / "방금 맞팔한 사람, 누굴까?" + 반쯤 가린 프로필 | 짝남 팔로잉 231 → 232 / 동일 |
| C4 친구 대화 | "야 너 남친 어제 어떤 여자랑 맞팔했던데?" → "이제 친구보다 체리가 먼저 알려줘요" | "야 너 짝남 어제 어떤 여자랑 맞팔했던데?" → 동일 |

C2의 알림 카드는 실제 알림톡 문구(`lib/services/cherry/notifications.ts`: "[체리] 등록하신 @maru.onair_ 계정에서 새 맞팔 2명을 확인했어요.")를 두 변형에 똑같이 쓴다.

공통 하단 요소: 체리 로고, "남친/짝남 맞팔 알리미 체리", "사전예약 · 선착순 300명".

## 6. 짝남(crush) 랜딩 교체표

원문은 `public/cherry/landing.html`과 3D 소스(`design/namchin-demand/three/`) 기준이다. *표시는 단순 치환이 아닌 Claude 제안 문구다.

## 7. 사용자 결정 (2026-11-23 확정)

1. **짝남 랜딩 교체표(§6):** 승인. 약속 2는 "인스타 아이디 하나면 돼요"로 수정하고, og 이미지도 짝남판으로 만든다.
2. **헤드라인 표현:** 광고는 두 변형 모두 "어떤 여자랑"으로 쓴다. 남친 랜딩 h1("누구랑")은 그대로 둔다.
   - 짝남 랜딩 h1도 "누구랑"으로 맞춘다(Claude 판단). 두 변형 모두 광고 "어떤 여자랑" → 랜딩 "누구랑"으로 같은 흐름이 된다.
3. **광고 카피(§5.6):** 승인.
4. **개인정보처리방침 추가 문구:** 승인(초안 그대로).
   - "체리 사전 예약 페이지는 광고 성과 측정을 위해 Meta Platforms, Inc.의 Meta 픽셀을 사용합니다. 페이지 방문과 사전 예약 완료 여부, 쿠키, 기기·브라우저 정보, 접속 IP가 Meta로 전송되며, 이메일과 휴대폰 번호는 전송하지 않습니다. 브라우저 쿠키 설정이나 Meta 광고 설정에서 거부할 수 있습니다."
   - 국외이전 표에 "Meta Platforms, Inc. / 미국"을 추가한다.
   - 법률 검토는 받지 않은 상태다.
5. **결제자 정의와 판정 기간(§5.4):** 판매 오픈 후 7일, 정가 결제 포함.
6. **사용자 직접 작업(남음)**
   - 메타 픽셀 ID를 발급해 Vercel `CHERRY_META_PIXEL_ID`에 등록
   - 이벤트 관리자에서 '자동 고급 매칭' 끄기
   - 광고 예산 설정
   - 프로덕션 DB 마이그레이션 적용 확인

## 8. 일정과 순서

1. 시안 PNG 완성 → 사용자가 메타에 광고를 등록해 심사를 받는다(심사는 배포와 병렬).
2. 코드 PR(랜딩 변형, 3D 재빌드, 추적, 콘솔, 개인정보처리방침) → 검토 → main 병합 → Vercel 배포.
3. 프로덕션 마이그레이션(`variant` 컬럼) 적용. 코드가 컬럼 없음을 견디므로 2와 순서가 바뀌어도 예약은 안전하다. 다만 컬럼이 생기기 전 예약은 변형이 null로 남는다.
4. 사용자가 픽셀 ID를 등록하고 자동 고급 매칭을 끈다 → Claude가 `?v=bf`, `?v=crush` 화면·픽셀 요청·DB 기록을 확인한다.
5. 4까지 확인된 뒤 광고를 켠다(목표 11/24). 그 전에 켠 광고의 클릭은 변형이 기록되지 않는다.

## 9. 후속 과제 (이번 범위 밖)

- 12/1 오픈 안내 메시지와 `/cherry/start`·결제 화면이 '남친' 문구라, crush 예약자는 결제 단계에서 메시지가 어긋난다. 결제 단계 비교를 공정하게 하려면, 오픈 안내를 변형별로 다르게 하거나 중립 문구로 바꿀지 12/1 전에 정해야 한다.
- 결제율 차이가 작으면 표본 부족일 수 있다. 메타 CAPI 도입이나 기간 연장은 결과를 보고 판단한다.
