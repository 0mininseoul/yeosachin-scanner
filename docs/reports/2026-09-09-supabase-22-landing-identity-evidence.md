## Database boundary

The migration enables and forces RLS on `public.landing_leads`, revokes table
privileges from `PUBLIC`, `anon`, `authenticated`, and `service_role`, and
exposes writes/claims/projection only through `SECURITY DEFINER` functions with
`SET search_path = ''` and `service_role` execution grants. The only DROP is
the explicitly reviewed replacement of the pre-existing
`landing_leads_context_shape_check`; no table, row, index, or function is
dropped.

The local PGlite contract applies the two predecessor migrations plus the new
migration and verifies target/excluded rows share one journey, capture replay
is idempotent, excluded replay does not duplicate, claims are monotonic,
conflicting owners are rejected, deletion fencing clears the owner, and a
fenced journey cannot be claimed again. The projection test also verifies a
context-filtered row retains the full journey row count.

Production migration dry-run/apply and production row-count/checksum parity
were not run. No remote migration was applied, and no production database
credentials or raw identity values were read or recorded. This is the only
rollout concern remaining before an operator-approved production dry-run.

## API and client boundary

`GET /api/admin/landing-leads` authenticates the cookie session, checks the
operator allowlist, accepts only the documented bounded filters, uses an
opaque signed keyset cursor, and returns a strict safe projection with
`Cache-Control: private, no-store`. Raw input, referrer, user agent,
principal/token hashes, internal UUIDs, IPs, and claim fields are stripped or
rejected before serialization. The dashboard has Target/Excluded tabs,
mapping-status and normalized Instagram/date filters, loading/error/empty
states, and keyset pagination; it uses the server API and never a browser
Supabase query.

The browser keeps the signed capture token only for the short handoff in
memory/session storage; server persistence receives only HMAC-derived hashes.
The preflight boundary repairs a missed lead capture, binds the target to the
exact preflight, copies the same journey to exclusions, and consumes the
handoff after an accepted request. OAuth claim is monotonic and the deletion
fence makes an unlinked journey permanently non-claimable.
