# Earlybird historical receipt cutover plan

Date: 2026-09-12
Scope: the 13-table cohort named below only. This is a read-only implementation design; no database mutation was run.

## Decision

Move the 21 historical rows into the existing `public.maintenance_jobs` archive contract, then remove the 13 source relations only after the active-writer decision and parity checks pass. Keep the public helper and outer RPC signatures stable, and replace each source-table lookup with a static, source-allowlisted projection from `maintenance_jobs.payload`; do not add a table, schema, or generic JSON facade.

The archive is historical evidence, not a queued job: every migrated row is `state = 'succeeded'`, has the complete typed source row in `legacy_row`, and keeps the source table name and exact primary-key object in the payload. Existing maintenance claim/finish/reconcile routines remain unchanged.

## Evidence boundary

- The pinned CLI was verified first: `npx --yes supabase@2.102.0 --version` returned `2.102.0`.
- Live reads used only the pinned linked CLI and `/private/tmp/yeosachin-public22-cli.0GC1rz`; queries returned catalog metadata and aggregates, never rows or identifiers.
- Aggregate source counts are 2, 1, 1, 1, 1, 7, 1, 1, 2, 1, 1, 1, 1 in the order listed below: 21 total.
- Live `maintenance_jobs` contained 23 rows before this cohort; its exact reviewed shape is 17 columns, including nullable `legacy_pending_user_id`, with RLS enabled and forced, with table grants revoked.
- Every cohort source has primary key `(order_id)`, RLS enabled and forced, and one immutable BEFORE UPDATE/DELETE trigger. Catalog evidence found no incoming foreign keys.
- PL/pgSQL table dependencies are not complete in `pg_depend`; the routine map combines sanitized live routine text with the local migration bodies and scoped app/script call-site search.

## Canonical archive contract

Use direct `INSERT ... SELECT` branches for all 13 relations. Do not call `enqueue_maintenance_job_v1`, because historical rows must enter terminal success rather than the live queue.

```sql
payload = jsonb_build_object(
  'legacy_source_table', '<one of the 13 literal names>',
  'legacy_primary_key', jsonb_build_object('order_id', source_row.order_id),
  'legacy_row', to_jsonb(source_row),
  'schema_version', 1
)
target_key_hash = hex(sha256(convert_to(
  'supabase-22-legacy-earlybird-retirement-v1:' || kind || ':' ||
  legacy_source_table || ':' || (payload->'legacy_primary_key')::text, 'UTF8')))
content_hash = hex(sha256(convert_to(payload::text, 'UTF8')))
```

Insert only `(kind, target_key_hash, state, payload, content_hash)` with `state = 'succeeded'`; existing defaults supply the remaining maintenance columns. Before insertion, abort on any same-key row unless state, payload, and content hash are all exactly equal. `ON CONFLICT DO NOTHING` is allowed only after that conflict guard. Validate the payload object, schema version, source literal, PK object, and every listed typed field before dropping a source.

## Transitive callers and behavior classification

- `create_or_replay_earlybird_fulfillment_request(uuid,uuid,bigint)` calls the snapshot receipt/count helpers and provider adoption readiness; its fulfillment idempotency behavior must not change.
- `earlybird_concierge_snapshot_conflict_counts_authorized` -> receipt authorization; the snapshot inspectors, dispatcher, local-job marker, completion RPC, and `create_or_replay_earlybird_fulfillment_request` all consume that gate.
- `earlybird_provider_run_adoption_ready_pre_first15` calls all six v2.11 readiness helpers; the exact resolver path reaches it through the `_pre_*` wrappers. `resolve_analysis_v2_exact_recovery_provider_run` also calls the v2.11 readiness helpers directly.
- `earlybird_v211_apify_transient_replay_ready` -> transient-failure readiness; policy-identity readiness -> Apify replay readiness; the remaining v2.11 readiness calls chain through provider adoption. Archive projections must therefore preserve NULL/not-found and boolean-false behavior exactly.
- `recover_earlybird_schema_failed_fulfillment(uuid)` calls provider adoption readiness and is invoked by `lib/services/earlybird/fulfillment-store.ts`; it is an active application state transition.
- `scripts/recover-earlybird-concierge-snapshot-conflict.ts` calls the snapshot recovery writer; `scripts/complete-earlybird-concierge-snapshot-conflict.ts` calls the inspectors/completion RPC; `scripts/correct-concierge-basic-result.ts` calls reviewed-source registration; `scripts/recover-first-payment-concierge.ts` calls publication. These are concrete operator/runtime dependencies.

Read-only helpers, inspectors, accessors, anti-dispatch gates, and resolver wrappers can be redirected in place without changing business behavior if their output, scope checks, SECURITY/ACL posture, and missing-row semantics are preserved. A writer that creates an analysis request, changes fulfillment/preflight/request state, registers reviewed source, or publishes a result cannot be replaced by a lookup redirect; it requires either call-site retirement or an archive-aware state-machine rewrite.

## Minimal static SQL change map

1. Begin one migration with the reviewed `lock_timeout = '5s'`, `statement_timeout = '2min'`, and the existing wave advisory lock. Verify `maintenance_jobs` exact columns/constraints, all 13 relation OIDs and exact typed shapes, RLS/trigger presence, and the expected public-table baseline before taking source locks.
2. Lock `maintenance_jobs` and all 13 sources in a deterministic name order. Recheck OIDs, source count, and the 21-row aggregate after the lock. Build one temporary expected table containing `(kind, source_table, payload, target_key_hash, content_hash)`.
3. Materialize 13 explicit `UNION ALL` branches, one per literal source table. Each branch uses `to_jsonb(source_row)` for the complete row and writes the exact `{order_id}` identity object; no dynamic SQL or polymorphic/generic JSON lookup is permitted.
4. Apply the domain-separated hashes above. Guard every existing `(kind,target_key_hash)` conflict for exact `state`, payload, and content hash; abort on duplicate source identity, malformed payload, unexpected count, or any non-succeeded conflict.
5. Insert archive rows as succeeded, then run aggregate parity checks: per-source count, distinct identity count, archive count, source-table label count, and a derived aggregate hash/boolean check. Do not emit identifiers, rows, payloads, hashes tied to individual rows, or other raw business data.
6. Replace bodies, not signatures, for the read surface. For each source, use a static `maintenance_jobs` branch constrained by both `kind` and literal `legacy_source_table`, then explicitly cast only the named fields required by that routine (`uuid`, `smallint`, `timestamptz`, `integer`, `text`, `varchar`, and `jsonb`). Preserve `IS DISTINCT FROM`, exact-count checks, scope joins, and no-match errors.
7. Rewrite `purge_expired_analysis_v2_preflights` with 13 explicit archive guard branches for every source preflight field listed below. Treat malformed or missing archive fields as a guard failure; never silently skip a retention reference.
8. Retire source-specific immutable triggers/functions only after all callers are closed and the archive/read parity checks pass. Drop relations without `CASCADE`; assert no incoming FK appeared between preflight and drop. Leave generic `maintenance_jobs` enqueue/claim/finish/reconcile routines untouched.

## Writers that may be retired versus larger changes

Conditional retirement candidates, after a final non-test call-site/incident-free check, are the one-shot rearm writers for adoption policy, PFE target, PFE3 media, terminal unavailable, and all six v2.11 rearm cohorts, plus profile-fetch recovery if its operator path is explicitly closed. Their helper functions can then be dropped with the source tables because no new incident should be admitted.

Do not simply drop now: `recover_earlybird_schema_failed_fulfillment` has an active service caller; snapshot recovery writer/inner/restore routines have active operational scripts; reviewed-source registration has an active correction script; and the first-payment publication path depends on the Apify transient recovery-source accessor. Closing those paths requires a coordinated caller change and state-machine decision. If any must remain callable after cutover, rewrite the writer to persist an allowlisted succeeded archive receipt before its state transition, with the same idempotency and conflict checks; that is a larger change than this cutover.

The Apify `read_earlybird_v211_concierge_recovery_source_v1()` accessor is not out of scope: despite its name, its body reads `earlybird_v211_apify_transient_replays`, so it must be archive-backed. The wrapper and publication routine stay intact. `bootstrap_earlybird_v211_concierge_first_order` occurrences of cohort names were literal/comment text only and require no change.

## FK retention and purge guards

There are no incoming FKs to these 13 tables. Every outgoing FK is `ON DELETE RESTRICT` and `ON UPDATE NO ACTION`; parents are `earlybird_orders(id)`, `analysis_requests(id)`, and/or `analysis_preflights(id)`. Preserve the parent retention effect explicitly after source removal:

- order parent: `order_id` in every source;
- request parents: adoption `original_failed_request_id`, `policy_failed_request_id`; PFE target `pfe_original_failed_request_id`, `rejected_successor_request_id`; PFE3 those two plus `media_failed_request_id`; profile/schema/terminal `failed_request_id`; Apify `original_failed_request_id`, `policy_identity_failed_request_id`, `transient_failed_request_id`; concierge `original_failed_request_id`, `first_relationship_failed_request_id`, `second_relationship_failed_request_id`; lease `failed_request_id`; policy `original_failed_request_id`, `policy_identity_failed_request_id`; profile-AI `original_failed_request_id`, `profile_ai_failed_request_id`; relationship `original_failed_request_id`, `relationship_failed_request_id`.
- preflight parents: snapshot `preflight_id`; adoption/PFE target/PFE3/terminal `rearmed_preflight_id`; profile/schema `recovery_preflight_id`; Apify/concierge/policy/profile-AI `failed_preflight_id` and `rearmed_preflight_id`; lease/relationship `source_preflight_id` and `rearmed_preflight_id`.
- nullable reviewed-source request/owner fields in the concierge replay row are archived in full; the catalog showed no FK on those nullable reviewed-source fields, so do not invent one during restoration.

The current purge body explicitly checks only selected source tables. Its preflight-delete phase must gain all branches above, plus the existing provider-run, order, waitlist, replay-capture, beta-allocation, and other guards. No scoped hard-delete path for orders or analysis requests was found; account deletion scrubs lifecycle data and is not part of this cohort. Any future parent purge must consult archived order/request fields before deleting.

## Batch, rollback, and evidence requirements

Twenty-one rows fit one transaction and one broad batch; the risk is DDL lock contention across 13 relations, not volume. Require deterministic locks, the 5-second lock timeout, 2-minute statement timeout, and an operator dry-run of catalog/aggregate checks immediately before apply. Production apply is coordinator-only through an isolated migration allowlist; never use `supabase db push --include-all` in a dirty worktree.
