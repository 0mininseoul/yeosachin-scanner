## 이 보드의 규칙

1. **가설은 반증 가능해야 한다.** "유저가 좋아할 것이다"는 가설이 아니다. "5명 중 3명 이상이 ~라고 답한다"가 가설이다.
2. **판정 기준은 실험 전에 고정한다.** 결과를 보고 기준을 옮기면 사후 해석이다.
3. **근거는 외부에서 독립적으로 들어와야 한다.** 우리가 만든 화면에서 우리가 만든 이벤트를 우리가 읽고 "검증됐다"고 하는 순환을 금지한다. rev.1이 정확히 이 순환에 빠졌다 — 팀이 만든 후기와 팀이 내린 설계 결정을 고객 증거로 취급했다. 각 실험의 *근거 출처* 칸이 이 규칙을 강제한다.
4. **코드를 쓰지 않는 실험이 항상 먼저다.**

## 지금 상태 (rev.3)

> **외부 가입 25명, 상당수가 플랜 화면 도달, 결제 0명.** 결제·결과 조회·공유는 전원 내부 테스터. (소유자 확인, 2026-07-31)
>
> **유입은 대부분 파운더가 직접 올린 Threads·X·에브리타임 글.** SEO는 세팅 1~2일차로 총 클릭 2·노출 4(일부 본인)라 기여 없음.

두 가지를 동시에 기억해야 한다.

1. **0/25는 "수요 없음"이 아니다.** 25명 기준 95% 신뢰구간 상한이 약 11%이고, 실제 전환율이 2%여도 0명이 나올 확률이 약 60%다. 도달자가 25명보다 적으면 구간은 더 넓다.
2. **더 중요한 건 그 25명이 누구였냐다.** 커뮤니티·소셜에서 파운더 글을 보고 온 사람은 정의상 재미·호기심 맥락이다. **우리는 재미 트래픽에 불안 해소 가격표를 붙여 시험했고 그게 0으로 나왔다. 썸·연애 중 특정 의심자는 아직 한 번도 만난 적이 없다.**

## H1 — 문제 가설 검증 (인터뷰) <a id="h1"></a>

**전체 설계·질문지·기록 시트·판정 기준은 [인터뷰 가이드](./2026-07-31-interview-guide.md)가 정본이다.** 여기서는 가설과 판정 조건만 요약한다.

### 검증 대상

| 가설 | 내용 |
|---|---|
| **H-A** 발견 | 여사친 관계를 **잘 몰라서** 불안하다 (기존 가설) |
| **H-B** 판정 | 잘 모르는 게 아니라 **이미 1~5명을 특정해 의심 중**이다 (메인 승격) |
| **H-C** 단계 조절 | **썸은 H-A, 연애는 H-B.** 관계 단계가 조절 변수다 |
| 대안 가용성 | 썸에서는 직접 묻기가 **아예 불가능**하다 |
| 지불 의사 | 타로·사주·궁합 등 이 불안에 **실제로 돈을 쓴 이력**이 있다 |
| 산출물 형태 | 그 결과를 **보관·공유**했다 (보고서 파일 가설) |

### 두 트랙

- **Track A — 이탈자 인터뷰**: 외부 25명 중 연락 가능한 사람. 남친 아이디까지 넣고 가격 화면을 본 뒤 나간 **유일한 외부 집단**. 핵심 질문 *"결제 화면 나오기 직전에, 뭐가 나올 거라고 생각하셨어요?"*
- **Track B — 콜드 문제 인터뷰**: 제품을 본 적 없는 **6명 = 썸 3 + 연애 3**. 5명이 아니라 6명인 이유는 H-C의 단계 비교가 이번 라운드의 핵심이기 때문이다

### 판정 기준 (사전 고정)

| 결론 | 조건 |
|---|---|
| H-B 채택 | 콜드 6명 중 4명 이상이 특정 인물 1~5명 지목, 그중 과반이 **우리가 묻기 전에 먼저** 언급 |
| H-A 채택 | 콜드 6명 중 4명 이상이 "모른다 / 떠오르는 사람 없다" |
| H-C 채택 | 썸 3명과 연애 3명의 판정이 **집단별로 갈린다** |
| 세그먼트 미성립 | 6명이 서로 완전히 다른 이야기를 한다 — 이것도 유효한 결과다 |
| 샘플 공개 가설 | Track A에서 "뭐가 나올지 몰랐다"류 응답이 과반 |

**오염 방지 4원칙**: ① 제품을 설명·제시하지 않는다 ② 미래 의향("쓰겠어?", "얼마면 살래?")을 묻지 않고 **과거 행동만** 묻는다 ③ 우리 어휘("의심", "위험", "여사친")를 먼저 꺼내지 않는다 ④ 의견이 아니라 행동을 묻는다.

**상태**: 미실행

| 항목 | 내용 |
|---|---|

| 왜 지금인가 | SEO가 이미 가동 중이라 **첫 외부 유입은 예고 없이 온다.** 그 코호트의 행동은 두 번 관측할 수 없다 |

| 완료 판정 | 같은 기간에 대해 서버 완료 이벤트 수 = `analysis_v2` terminal 성공 요청 수. 클라이언트 이벤트와의 차이가 그동안 놓친 양이다 |
| 근거 출처 | Supabase 원장(결제·이행과 같은 SSOT)과 Amplitude의 교차 검증 |
| 상태 | 프롬프트 작성 완료, 백엔드 인계 대기 |

> Session Replay를 민감 경로로 확대하는 것은 **대안이 아니다.** `/`, `/privacy`, `/terms`만 허용하는 현재 결정은 옳고 되돌리지 않는다. 관찰은 리플레이가 아니라 서버 이벤트(H0)와 대면 인터뷰(H1)로 얻는다.

## H2 — 첫 외부 실결제 <a id="h2"></a>

rev.1은 "실결제가 존재하는가"를 물었다. **소유자가 답했다 — 외부 실결제는 아직 없다.** 가설을 다시 세운다.

| 항목 | 내용 |
|---|---|
| 새 가설 | 내부 테스터가 아닌 외부 유저의 reference-confirmed 실결제가 발생한다 |
| 실험 | `npm run report:earlybird-demand -- --start <date> --end <date>` 를 주기적으로 실행 |
| 판정 기준 | 확정 수요 건수. 리다이렉트·클라이언트 이벤트·수동 연결·waitlist는 세지 않는다(리포트가 이미 이 경계를 강제한다). **내부 테스터 계정을 명시적으로 제외**한 수치여야 한다 |
| 근거 출처 | Groble 결제 증거 + seller reference 이중 확인. **외부 결제사가 진실의 출처**라 순환이 없다 |
| 주의 | 1건이 발생해도 "수요 검증"이 아니다. **경로가 작동한다는 것만** 증명한다. 그 1명이 왜 샀는지는 반드시 따로 물어야 한다 (그때는 결제 동기 인터뷰가 비로소 가능해진다) |
| 선행 | H0(그 사람의 행동을 기록할 수 있어야 한다), R1 처리(가짜 후기를 보고 산 결제는 제품에 대한 신호가 아니다) |
| 상태 | 미발생 |

| 항목 | 내용 |
|---|---|

## H7 — 결과 공유가 실제 유입을 만드는가 <a id="h7"></a>

| 항목 | 내용 |
|---|---|
| 현재 상태 | **공유본 조회도 전원 내부 테스터.** 공유 루프는 아직 한 번도 외부에서 작동한 적이 없다 |
| 가설 | `/share/[token]` 링크를 통한 외부 유입이 신규 결제로 이어진다 |
| 왜 중요한가 | §7의 원가 구조상 유료 획득만으로 버티기 어렵다. 공유가 죽어 있으면 획득 전략을 전적으로 SEO/커뮤니티에 걸어야 한다 |
| 실험 | `result_shared` → 공유 링크 유입 → 신규 `target_submitted` → 결제 경로 측정 |
| 판정 기준 | 공유 1건당 신규 외부 유입 수. 1 미만이면 바이럴이 아니라 부가 기능으로 대우한다 |
| 제약 (중요) | 공유 페이지의 제3자 노출은 사고 이력이 있다(`0f7e545 fix(share): stop shipping third-party bios`). **공유 최적화가 제3자 노출 확대로 이어지면 안 된다.** R2 정책 확정이 선행 |
| 선행 | H0, R2, 첫 외부 유입 |
| 상태 | 미실행 |
