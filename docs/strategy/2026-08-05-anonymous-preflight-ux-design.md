# 로그인 시점 이전(移轉) UX 설계 — 익명 preflight

- 작성일: 2026-08-05
- 근거: [린 캔버스 ⑧ 실측 퍼널](./2026-07-31-lean-canvas.md)
- 상태: **로그인 시점을 결제 직전으로 옮기는 익명 preflight·상태 복원은 production 배포 완료. 이 문서가 함께 제안한 샘플 리포트는 아직 미구현이며, 현재 계약은 [유료 분석 E2E 설계 §12](../superpowers/specs/2026-08-10-revenue-e2e-observability-design.md#12-결제-전-demo-preview)가 대체한다.**

## 왜 하는가

실측 퍼널(관리자 제외, 2026-07-01~08-05):

```
target_submitted 108  →  auth_completed 27   (25.0%, −81명)
                                ↓
                         plan_viewed 18
```

**아이디를 입력한 108명 중 81명이 로그인에서 이탈한다.** 플랜~결제 전체 손실(15명)의 5배가 넘는다.

그리고 **가격을 본 사람이 18명뿐**이다. 이 표본으로는 가격 가설을 검증할 수 없다. 로그인을 뒤로 미루는 진짜 목적은 이탈 감소가 아니라 **가격을 보는 사람 수를 세 자리로 만드는 것**이다.

과거 로그인 벽은 **남자친구의 인스타그램 아이디를 입력한 직후**에 카카오·구글 인증을 요구했다. 아직 아무 가치도 주지 않은 시점이라 사용자가 민감한 탐색 직후 신원을 요구받는 구조였다.

## 두 안 비교

### A안 — preflight 결과에서 로그인 (블러 + 로그인 박스)

익명 preflight → 결과 화면 하단에 데모 데이터 블러 + 카카오 로그인 박스 → 로그인 시 데모·플랜 공개.

- ✅ "로그인하면 이게 열린다"는 보상 계약이 명확
- ❌ **가격 노출이 여전히 로그인 통과율에 묶인다.** 통과율이 25%→50%로 올라도 가격을 보는 사람은 50명대에 그친다
- ❌ **블러 대상이 데모 데이터다.** 남의 샘플을 가리는 건 정보량이 0이고 "내 것"에 대한 궁금증을 만들지 못한다. 블러가 작동하려면 *본인 데이터*를 가려야 하는데, preflight 단계에는 본인 결과가 존재하지 않는다 — 관계 수집은 결제 후에 일어나기 때문이다

### B안 — 결제 클릭에서 로그인 (권고)

로그아웃 상태로 preflight 결과 + 샘플 리포트 + 플랜/가격까지 전부 공개 → **[결제하기]를 눌렀을 때** 로그인 모달 → 로그인 후 주문 생성 → Groble 결제창.

- ✅ **가격 노출이 로그인에서 완전히 분리된다.** 가격을 본 사람이 108명 규모가 될 수 있다
- ✅ 로그인 요구가 "결제하려면 계정이 필요하다"는 **누구나 납득하는 맥락**에 놓인다. 게이트가 아니라 절차로 읽힌다
- ❌ 상태 복원 구현이 더 복잡하다 (OAuth 리디렉트를 건너 preflight·플랜 선택을 보존해야 함)

> **권고: B안.** 지금 가장 필요한 학습이 가격 반응이고, A안은 그 학습을 로그인 통과율에 계속 묶어둔다.

### C안을 찾아봤으나, 별도 안으로 성립하는 것은 없었다

세 가지를 검토했고 전부 기각하거나 B안에 흡수했다.

**C-1. 게스트 결제 (로그인 아예 없음).** Groble 결제는 외부 결제창이고 전화번호 매칭 로직이 이미 있으므로 이론상 가능하다. 결제 후 magic link로 결과를 열어주는 형태.
→ **기각.** 결과에 제3자 개인정보가 담겨 있어 접근 통제가 약해지는 것을 감수할 수 없다. magic link 유출은 곧 남의 분석 결과 노출이다. 결제 시점 로그인은 이미 납득되는 마찰이라 이득 대비 리스크가 크다.

**C-2. 인증 수단 변경 (전화번호·이메일 OTP).** 카카오 로그인 마찰의 일부가 "내 카카오 계정이 이 서비스에 연결된다"는 심리적 부담일 수 있다.
→ **기각하되 부분 흡수.** 근거 없이 인증 수단을 바꾸는 건 위험하고, 전화번호 OTP는 오히려 더 무겁게 느껴질 수 있다. 다만 **로그인 모달 카피에 "무엇이 저장되고 상대에게는 알려지지 않는다"를 명시**하는 것은 값싸고 효과 가능성이 있어 B안에 포함한다.

**C-3. preflight를 뒤로 미루고 샘플·가격을 먼저.** 아이디 입력 → 샘플+가격 → [이 계정으로 진행] → preflight → 결제. 이러면 preflight 실패자(현재 50%)도 가격을 보므로 노출이 108명에 더 가까워진다.
→ **기각하되 부분 흡수.** 치명적 결함이 있다. **preflight 전에는 플랜 적격성을 모른다.** 계정 규모에 따라 Basic/Standard/Plus가 갈리므로 정확한 가격을 제시할 수 없고, "990원부터" 같은 범위로만 보여주게 된다. **가격 반응을 측정하려는데 부정확한 가격을 보여주면 학습이 오염된다.**
다만 부분은 살릴 수 있다 — **preflight 실패 화면에도 샘플과 가격대를 노출한다.** 실패한 사람도 제품을 이해하고 나가며, 다른 계정으로 재시도할 동기가 생긴다. 부작용이 없으므로 B안에 포함한다.

## B안 플로우

```
① 랜딩 /
   남친 인스타 아이디 입력 → [판독 시작]          ← 로그인 요구 제거
        ↓
② 본인 계정 제외 화면 (익명)                      ← 기존 exclusion 단계 유지
        ↓
③ preflight 실행 (익명)
   대상 계정 확인 + 플랜 적격성 판정
   실패 시 사유별 안내 (VALIDATION_ERROR 세분화 선행 필요)
        ↓
④ preflight 결과 + 샘플 리포트 + 플랜/가격        ← 전부 로그아웃 상태
        ↓
⑤ [결제하기] → 로그인 모달 → preflight claim → 주문 생성 → Groble
```

## 반드시 풀어야 할 5가지

### 1. 익명 preflight 소유권 이전 (claim)

- preflight를 `user_id NULL`로 생성하고, 서명된 claim token을 클라이언트에 발급한다
- 로그인 완료 후 그 토큰으로 `user_id`를 채운다
- **스키마 확인 필요**: `analysis_preflights.user_id`가 현재 NOT NULL이면 forward migration 필요
- `earlybird_orders.preflight_id`가 `NOT NULL UNIQUE REFERENCES ... ON DELETE RESTRICT`이므로, 주문 생성은 claim이 끝난 뒤여야 한다
- claim token은 **일회용·단기 만료**로 두고, 이미 claim된 preflight의 재claim은 거부한다 (타인 preflight 탈취 방지)

### 2. OAuth 리디렉트 상태 복원 — 가장 흔한 실패 지점

카카오 로그인은 페이지를 떠난다. 돌아왔을 때 **preflight_id, 선택한 plan_id, exclusion 결정**이 살아 있어야 한다.

- `sessionStorage`만으로는 부족하다. 일부 인앱 브라우저(카카오톡 웹뷰 등)에서 유실된다
- **claim token을 OAuth `state` 또는 콜백 redirect URL에 실어야 안전하다.** 기존 `storePendingAnalysisTarget` 패턴을 확장하되 서버 왕복에 의존하도록 바꾼다
- **복원 실패 시 처음부터 다시 시작하게 되면 지금보다 나쁘다.** 이 경로의 회귀 테스트가 필수다

### 3. 익명 preflight는 Apify로 — 버너 계정 리스크 격리 (채택)

지금은 로그인이 사실상 rate limit 역할을 한다. 그걸 없애면 방어가 필요하다.

> **가장 중요한 이유는 원가가 아니라 계정 정지 리스크다.** 유료 경로가 지정 버너 계정의 인증 세션(`selfhosted_auth`)을 쓰므로, Instagram 요청 수가 늘면 계정 정지 확률이 올라간다. **정지되면 유료 경로 전체가 동시에 멈춘다.**

**해법: 익명 preflight의 대상 프로필 summary만 Apify로 라우팅한다.**

- 계정 하나의 profile summary라 건당 `$0.0026` 수준. 108건 기준 약 $0.28로 무시할 만하다
- **효과가 원가 절감이 아니라 리스크 격리에 있다.** 버너 계정을 결제한 사용자의 분석에만 쓰게 되어 **계정 리스크가 매출과 연동된다** — 돈 낸 만큼만 계정을 태운다
- 기존 preflight 원장·상한 메커니즘(`analysis_preflight_provider_runs`, `maxTotalChargeUsd`, 30초 후 실제액 정산)을 그대로 재사용한다
- 현재 유료 경로가 `selfhosted_auth` 전용이므로 **명시적 예외 경로로 provider selector를 분리**해야 한다

그래도 함께 필요한 것:

- IP·디바이스 기준 rate limit (이제는 계정이 아니라 **비용 폭주** 방어)
- 동일 타겟 **preflight 스냅샷 TTL 재사용** (같은 계정을 여러 명이 조회해도 외부 요청은 1회)
- 익명 preflight 일일 상한과 초과 시 로그인 요구로 폴백하는 안전판

### 4. 계측

- `plan_viewed`, `plan_selected`를 **익명 상태에서도 발화**한다. 안 그러면 이 변경의 효과를 측정할 수 없다
- **로그인 후 Amplitude identity merge를 반드시 검증한다.** 익명 이벤트가 로그인 후 올바른 Supabase UUID로 병합돼야 한다. 이건 이미 발견된 identity 버그(`payment_confirmed_viewed` 오계상)와 같은 뿌리이므로 함께 고친다
- 신규 이벤트 권장: `login_prompted` (결제 클릭으로 로그인 모달이 뜬 시점) — 로그인 요구 지점의 이탈을 별도로 본다

### 5. 결제 직전 로그인 이탈 대비

- 로그인 모달에 **이유를 명시**한다. "결제 내역 확인을 위해 계정이 필요해요" 수준이면 충분하다. 이유 없는 로그인 요구가 이탈을 만든다
- 로그인 취소·실패 시 ④ 화면으로 **정확히 복귀**한다 (선택한 플랜 유지)

## 출시 — 한 번에 바꾼다 (초안의 단계 분리는 철회)

초안은 로그인 위치와 샘플을 순차 출시해 효과를 분리하자고 했다. **철회한다.** 세 가지 이유로 틀렸다.

1. **샘플은 선택 기능이 아니라 결제의 전제조건이다.** 한 번도 본 적 없는 것에 돈을 내지 않는다. 샘플 없는 1단계는 **전환되지 않을 것을 알면서 출시하는 버전**이고, 거기서 얻는 학습은 우리가 유지할 생각도 없는 구성에 대한 것이다.
2. **유저는 재생 가능한 자원이 아니다.** 유입이 파운더 개인 채널이라 특히 그렇다. 1단계에 100명을 태우는 것은 그 100명을 실패가 예상되는 구성에 소모하는 것이다.
3. **표본이 애초에 분리 검증을 감당하지 못한다.** 구간당 100명 규모로는 두 레버의 효과를 통계적으로 가를 수 없다.

### 그런데도 효과는 구분된다 — 퍼널 구간이 이미 다르기 때문

동시에 바꿔도 두 레버는 **서로 다른 구간에 나타난다.**

| 레버 | 나타나는 구간 |
|---|---|
| 로그인 위치 이전 | `target_submitted` → `plan_viewed` |
| 샘플 리포트 | `plan_viewed` → `plan_selected` → `checkout_started` |

로그인은 플랜 화면 **앞**의 관문이고 샘플은 플랜 화면 **위**의 설득 재료다. 순차 출시 없이도 귀속이 된다. 초안은 이 점을 놓쳤다.

## 선행 조건

| # | 항목 | 이유 |
|---|---|---|
| 1 | **preflight 실패 사유 세분화 로깅** | 현재 `preflight_started` 26명 중 13명이 `VALIDATION_ERROR`인데 닫힌 enum이라 원인 구분이 안 된다. 익명화하면 이 실패가 더 앞단으로 나오므로 먼저 봐야 한다 |
| 2 | **Amplitude identity merge 수정** | 익명→로그인 병합이 깨져 있으면 이 변경의 효과를 측정할 수 없다 |
| 3 | 버너 계정 rate limit·캐시 | 익명 개방 전에 방어가 있어야 한다 |

## 열린 질문

- `analysis_preflights` 원장에 고유 user가 5명뿐인데 Amplitude `preflight_started`는 26명이다. **VALIDATION_ERROR가 preflight 행 생성 전에 거부되는지, 아니면 purge로 지워지는지** 확인이 필요하다. 전자라면 실패 사유를 사후 분석할 서버 원장이 아예 없다는 뜻이다
- 익명 preflight 결과를 얼마나 오래 유지할 것인가 (TTL과 claim 만료의 관계)
