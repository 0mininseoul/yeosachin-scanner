# selfhosted_auth 전략 재검토 보고서

- 작성일: 2026-08-06
- 목적: 이 세션에서 진행한 selfhosted_auth 검토·실측 결과를 전략 수립 세션에 전달
- 상태: **역사적 실측 보고서. 현재 운영 결정은 [8월 매출 우선 운영 전략](./2026-08-08-revenue-first-operating-strategy.md)이 대체함**

## 1. 결론 요약

현재까지의 증거만으로 `selfhosted_auth`가 기술적으로 항상 불가능하다고 결론 내릴 수는 없다. 실제로 인증 수집 단계에서 팔로워·팔로잉·좋아요·댓글 데이터가 여러 차례 반환된 기록이 있다.

그러나 다음 사실도 동시에 확인됐다.

- 완전한 분석 결과까지 도달한 selfhosted_auth E2E 성공 기록은 아직 없다.
- 같은 계정에서도 인증 수집이 성공한 날과 Instagram 인증 엔드포인트가 `401`/`PleaseWaitFewMinutes`로 거절된 날이 있었다.
- 인증 수집이 성공한 요청들도 후속 분석 파이프라인의 checkpoint/evidence 계약 오류로 최종 실패했다.
- 따라서 현재의 단일 계정·단일 세션·instagrapi 기반 구조는 유료 프로덕션 운영을 승인할 수준의 신뢰도를 입증하지 못했다.

전략적 판정은 다음과 같다.

> `selfhosted_auth-only`를 지금 정식 유료 운영 경로로 확정하는 것은 NO-GO다. 다만 3개 계정부터 시작하는 계정 풀 파일럿은, 현재 서비스의 데이터 범위를 유지하면서 외부 스크래핑 비용을 줄일 수 있는 유일한 현실적 실험 경로이므로 별도 검증할 가치가 있다.

3개 계정 파일럿이 성공하기 전에는 5개 계정 동시 운영이나 5건 동시 분석을 약속하지 않는다.

## 2. 사업·제품 제약

이 전략 검토의 전제는 다음과 같다.

- 분석 1건당 스크래핑 운영비를 `$0.1` 이하로 낮춰야 한다.
- 유료 분석 후 Apify 비용을 지속적으로 지출하는 구조는 마진상 유지하기 어렵다.
- preflight 이후의 유료 수집은 selfhosted_auth로 처리하고 싶다.
- 현재 서비스가 필요로 하는 데이터는 대상의 프로필·피드뿐 아니라 팔로워/팔로잉 목록, 좋아요 사용자, 댓글 데이터까지 포함한다.
- 현재 데이터 계약에서 Meta 공식 API는 임의 대상 계정의 관계 목록·게시물 상호작용을 그대로 대체하는 경로로 취급하지 않는다. 따라서 공식 API는 단기 대체재가 아니라 장기적인 제품 범위 재설계 옵션으로만 둔다.
- 현재 트래픽은 낮지만 향후 최대 5건의 요청을 처리할 수 있는 구조를 원한다.

## 3. 검토한 현재 구조

현재 배포된 인증 워커는 하나의 세션 설정과 하나의 계정 작업 mutex를 중심으로 동작한다.

- `max_in_flight=5`는 호출 대기열의 상한이지 계정 5개를 병렬로 쓰는 기능이 아니다.
- 실제 계정 작업은 operation lock으로 직렬화된다.
- 인증 run의 account slot은 현재 `primary` 하나로 제한되어 있다.
- 인증 실패·rate limit·challenge 상태는 durable safety state에 기록되고, 실패 상태를 자동으로 지우거나 즉시 재시도하지 않도록 설계돼 있다.
- 유료 경로는 `selfhosted_auth`를 사용하고 Apify 자동 fallback은 꺼져 있었다.

따라서 3~5개 계정 풀은 환경변수 몇 개를 추가하는 수준이 아니다. 계정별 세션, 워커 lane, queue, mutex, cooldown/quarantine, receipt ledger, health routing, 장애 복구를 분리하는 별도 아키텍처 작업이다.

현재 provider scope ledger는 계정 풀·세션 rotation·proxy/evasion 경로를 descoped 상태로 기록하고 있다. 계정 풀을 채택하려면 이 문서의 전략 승인을 먼저 내리고, 그 이후에 ledger와 운영 runbook을 명시적으로 갱신해야 한다.

## 4. 실측 데이터

### 4.1 초기 인증 실측

Supabase의 `analysis_v2_selfhosted_auth_runs`와 연결된 분석 요청 기록을 집계한 결과다. 원본 계정명·요청 ID·세션 값은 이 문서에 기록하지 않는다.

#### 2026-08-04

- 팔로잉 수집 run 4회
- 각 run에서 약 643개 항목 반환
- 팔로워 측 run은 기록되지 않음
- 분석 요청은 `SCRAPING_INCOMPLETE_ERROR`로 종료

해석: 인증 계정으로 한쪽 관계 목록을 반환받는 것까지는 확인했지만, 양쪽 관계 목록을 완성하지 못해 분석 전체가 실패했다. 이 기록만으로 Instagram이 팔로잉을 차단했다고 단정할 수는 없으며, 당시에는 관계 수집·파이프라인 완료 조건이 함께 충족되지 않았다.

#### 2026-08-05

총 14개 분석 요청에 인증 수집 기록이 남아 있다.

- 13개 요청: 팔로워 약 469~472개와 팔로잉 약 643~644개가 모두 반환됨
- 1개 요청: 팔로잉 측만 반환됨
- target liker 수집 run 5회: 각 약 343개 항목
- target comment 수집 run 6회: 각 24개 항목
- 모든 요청의 최종 상태는 `failed`

최종 실패 코드는 `ANALYSIS_V2_JOB_HANDLER_FAILED`, `ANALYSIS_V2_EVIDENCE_INVALID`, `ANALYSIS_V2_PROFILE_EVIDENCE_INCOMPLETE` 등으로 나뉘었다.

해석: 8월 5일에는 selfhosted_auth의 관계·상호작용 수집 단계 자체가 여러 번 성공했다. 그러나 checkpoint/evidence 계약, 후속 job handler, profile evidence 조건 등 downstream pipeline 오류가 최종 E2E를 막았다. 따라서 이 날짜의 실패를 모두 Instagram 인증 실패로 분류하면 안 된다.

### 4.2 최근 E2E

가장 최근의 Standard 검증에서는 다음 순서로 진행됐다.

1. preflight 및 selfhosted 프로필 배치 수집 성공
2. 프로필 배치의 외부 provider 비용 기록 없음
3. 인증 팔로워 수집 성공
4. 인증 팔로잉 수집에서 Instagram `401` 및 `PleaseWaitFewMinutes`
5. 인증 워커가 502를 반환하고 이후 상호작용 요청 일부가 423으로 잠김
6. 분석 요청이 `SCRAPING_INCOMPLETE_ERROR`로 종료

이 시도에서는 Apify fallback이 꺼져 있었고, 프로필 수집에 대한 Apify 비용도 확인되지 않았다.

해석: 최근 실패는 이전의 downstream pipeline 오류와 달리, Instagram 인증 세션/계정 상태가 직접 드러난 사례다. 공식 앱에서 계정 제한이 없다고 표시돼도 비공식 인증 엔드포인트의 상태까지 정상이라는 뜻은 아니다.

### 4.3 보조 증거: 로그인 없는 selfhosted 프로필 경로

7월의 별도 V2 canary에서는 Cloud Run 데이터센터 egress에서 로그인 없는 프로필 요청이 대규모로 `429`를 받아 selfhosted 성공 0건이 기록된 적이 있다. 이후 전역 pacing gate와 circuit이 추가됐고, 최근 단일 preflight 프로필 배치는 성공했다.

이 자료는 인증 관계 수집과는 별개의 문제지만, selfhosted 경로 전반에서 “한 번 성공한 요청”을 곧바로 운영 SLA로 해석하면 안 된다는 근거다.

## 5. 실측에 대한 자체 평가

### 확인된 긍정 신호

- 인증 worker와 receipt/ledger 경계는 실제 데이터를 반환했다.
- 팔로워·팔로잉 양쪽을 모두 반환한 요청이 8월 5일에 반복적으로 있었다.
- 좋아요·댓글 수집도 일부 요청에서 항목이 반환됐다.
- 프로필 selfhosted 성공 시 외부 스크래핑 비용을 0으로 만들 수 있다.
- 계정별 cooldown/quarantine을 두면 단일 계정 장애를 서비스 전체 장애로 즉시 전파하지 않도록 설계할 수 있다.

### 확인된 부정 신호

- 현재까지 최종 분석 결과를 반환한 selfhosted_auth E2E가 없다.
- 계정 상태가 시간에 따라 변하고, 최근에는 팔로잉 엔드포인트가 직접 거절됐다.
- 세션 생성 과정에서 공식 앱 승인 챌린지와 자동화 활동 경고가 반복됐다.
- 인증 수집이 성공해도 후속 파이프라인이 별도로 실패할 수 있다.
- 현재 구현은 계정 1개만 지원하고, 5건 동시 분석을 보장하지 않는다.
- 동일 IP·기기·행동 패턴으로 여러 계정을 운용할 때 실패가 계정 간 상관될 가능성을 측정한 자료가 없다.

## 6. 3~5개 계정 풀 전략 평가

### 기대 효과

- 계정 한 개가 cooldown/quarantine에 들어가도 다른 계정으로 대기열을 처리할 수 있다.
- 계정별 세션 상태와 장애 원인을 분리할 수 있다.
- 계정당 동시 작업을 1개로 제한하면서 전체 처리량을 점진적으로 늘릴 수 있다.

### 핵심 위험

- 여러 계정을 사용한다고 Instagram의 계정·IP·행동 기반 제한이 독립적으로 동작한다는 보장은 없다.
- 새 계정도 세션 발급 챌린지를 받을 수 있다.
- 계정별 비밀값·세션·복구 절차를 운영해야 한다.
- 계정 rotation을 잘못 구현하면 중복 실행·비용 대사·결과 귀속이 깨질 수 있다.
- 3개 계정이 모두 건강하지 않으면 5건 동시 처리 목표는 달성되지 않는다.

### 기술적 요구사항

계정 풀을 실제로 도입하려면 최소한 다음이 필요하다.

1. 계정별 독립 worker lane 또는 명시적 session slot
2. 계정별 durable mutex와 cooldown/quarantine
3. 요청 시작 시 slot을 고정하고, 실행 중 계정을 바꾸지 않는 routing
4. follower/following/liker/comment run의 account slot 영속 기록
5. ambiguous timeout을 자동 재실행하지 않는 reconciliation
6. 계정별 health 상태와 수집 coverage 관측
7. 장애 계정 격리와 수동 복구 절차
8. 계정 풀 전체에 적용되는 낮은 수준의 global pacing
9. 3개 계정에서 5개 계정으로 확장할 때의 migration/rollback 절차

계정 풀은 “차단 회피 기능”이 아니라 “장애 격리와 가용성 실험”으로 정의해야 한다. 계정·네트워크를 빠르게 바꾸는 방식은 성공률을 입증하는 방법으로 사용하지 않는다.

## 8. 권고하는 검증 순서

### Phase 0 — 현 상태 보류

- selfhosted_auth-only 유료 프로덕션을 성공 경로로 홍보하지 않는다.
- 현재 계정의 자동화 경고 상태에서 반복 재시도하지 않는다.
- 기존 Apify/selfhosted 구현은 삭제하지 않는다.
- 현재 프로덕션 접수 게이트가 열려 있더라도, 인증 수집이 안정화될 때까지 유료 실사용을 성공으로 간주하지 않는다.

### Phase 1 — 3개 계정 파일럿

- 계정 3개를 준비하되, 처음에는 계정당 동시 작업 1개만 허용한다.
- 계정별로 세션 발급, 팔로워, 팔로잉, 좋아요, 댓글을 독립 검증한다.
- 이후 downstream pipeline 오류를 정리한 배포본으로 전체 E2E를 실행한다.
- 3개 계정의 health 상태를 분리 기록한다.

### Phase 2 — 제한된 동시성 검증

- 3개 계정으로 3건 동시 분석을 먼저 검증한다.
- 5건 동시 분석은 5개 계정 모두가 건강하고, 각 계정이 단일 요청을 안정적으로 완료한 뒤에만 검토한다.
- 동시성 테스트에서 한 계정의 실패가 다른 계정의 receipt·queue·result에 영향을 주지 않는지 확인한다.

### Phase 3 — 승격 또는 중단

다음 조건을 모두 충족할 때만 selfhosted_auth를 정식 경로로 승격한다.

- 3개 계정 각각에서 전체 E2E 3회 연속 완료
- 48시간 관찰 동안 `401`, `429`, `PleaseWaitFewMinutes`, challenge, 자동화 활동 경고 없음
- followers/following 각각 선언 수 대비 99% 이상 coverage
- duplicate run·receipt·queue task·결과가 0건
- 전체 wall time p95가 플랜 SLA 이내
- selfhosted 수집 비용과 GCP/Gemini 비용을 분리 측정하고, 목표 원가를 충족
- downstream pipeline 오류 없이 최종 result re-entry까지 성공

어느 계정에서든 반복적인 인증 거절이나 보안 경고가 발생하면 해당 계정을 격리하고 자동 rotation하지 않는다. 3개 계정 파일럿이 시간 제한 내 승격 기준을 통과하지 못하면, 현재 데이터 범위를 유지한 무외부비용 모델은 보류하고 제품 범위 또는 가격·원가 전략을 다시 결정한다.

## 9. 전략 세션에서 결정해야 할 질문

1. 3개 계정 lane 구축에 필요한 운영 복잡도와 유지비를 감수할 것인가?
2. 스크래핑 비용 `$0.1` 이하라는 목표가 GCP·Gemini·계정 관리 비용까지 포함한 총원가인지, 외부 provider 비용만을 뜻하는지?
3. 3개 계정 파일럿이 실패할 경우 서비스 기능 범위를 축소할 수 있는가?
4. 외부 fallback을 완전히 금지할 것인지, 실패 건에만 제한적으로 허용할 것인지?
5. 전체 E2E 3회 연속 성공과 48시간 관찰을 유료 런칭의 필수 gate로 승인할 것인가?
6. 5건 동시성보다 낮은 동시성과 대기열을 허용해 초기 운영을 시작할 수 있는가?

## 10. 최종 전략 문장

현재 증거는 selfhosted_auth를 폐기할 정도로 부정적이지 않지만, 정식 런칭을 승인할 정도로 긍정적이지도 않다. 인증 수집 자체는 여러 번 성공했으나, 계정 상태의 변동성과 downstream pipeline 실패가 함께 존재한다.

따라서 selfhosted_auth는 당장 상용 성공 경로가 아니라, 3개 계정 장애 격리 파일럿으로 재정의한다. 3개 계정에서 재현 가능한 전체 E2E 성공과 원가·SLA 측정이 확인될 때만 5개 계정 및 동시성 확장을 검토한다. 그 gate를 통과하지 못하면 공식 API를 억지로 대체재로 간주하지 말고, 외부 provider 비용을 받아들이거나 제품이 요구하는 데이터 범위를 줄이는 방향으로 전략을 전환한다.
