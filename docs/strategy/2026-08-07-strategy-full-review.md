## 현재 적용 상태 (2026-08-10)

이 문서가 작성된 다음 날 외부 사용자의 Basic 990원 실결제가 발생했고, 결과는 concierge 복구 뒤 구매자가 보관함에서 직접 확인했다. 따라서 아래 rev.2의 `첫 E2E`·가격·출시 순서 결론은 현재 운영 결정으로 사용하지 않는다.

현재 적용하는 정정은 다음과 같다.

1. 판독기는 Basic 990원 / Standard 1,990원의 제한 재고를 열어 두고 Apify concierge로 판매한다. 정상 전달 5건과 플랜별 p95 원가 전에는 2,900원 / 4,900원으로 바로 올리지 않는다.
2. 맞팔 알리미는 판독기의 완전 안정화를 기다리지 않고 30일 유료 concierge 파일럿을 병행 준비한다.
3. 공개 맞팔이 상세 상한을 넘을 때만 관계 payload의 **`profile_pic_url`과 `fullname`**으로 1차 라우팅한다. 상한 이하면 전원을 상세 분석하며 bio·username·기존 프로필 캐시 전수 조회는 사용하지 않는다.
4. Basic 100명 / Standard 200명 상한은 최종 성별을 강제하기 위한 컷이 아니라 상세 profile·media·interaction 대상으로 보내는 라우팅 상한이다. 상한 밖은 `not_screened`, 상한 안의 최종 미상 30%는 coverage gate이며 정확도는 blind audit로 따로 본다.
5. selfhosted_auth는 매출 선행 조건이 아니다. Apify E2E가 복구된 뒤 버너 2~3개로 별도 canary를 통과해야 전환 후보가 된다.

아래 본문은 위 결론에 이르는 2026-08-07 당시 계산과 반론 기록으로만 보존한다.

## 1. 정정 — 계정 풀을 잘못 읽었다

rev.1은 계정 풀을 **동시 요청 가용성** 문제로 읽고 *"수요가 0이니 불필요"*라고 기각했다. 소유자가 말한 것은 그게 아니었다.


| 용도                      | 목적                                                       | 수요와의 관계                                    |
| ----------------------- | -------------------------------------------------------- | ------------------------------------------ |
| **(A) 동시 가용성**          | 여러 유저 요청을 여러 계정으로 분산                                     | 수요가 있어야 의미 있음 → rev.1의 기각은 **여기서는 여전히 유효** |
| **(B) 단일 분석의 요청 예산 분할** | **한 건**의 followers/following/liker/comment를 서로 다른 계정에 배분 | **수요와 무관.** 1건도 완주 못 하면 필요하다               |


**소유자가 말한 것은 (B)이고, rev.1은 (A)로 반박했다. 내 오독이다.**

### (B)를 지지하는 실측

재검토 보고서 §4.2의 최근 E2E 순서가 정확히 이 그림이다.

```
1. preflight 성공
2. 프로필 배치 성공
3. 인증 팔로워 수집 성공        ← 여기까지 같은 계정
4. 인증 팔로잉 수집 401 + PleaseWaitFewMinutes   ← 같은 계정, 같은 분석 안에서 소진
5. 워커 502, 이후 상호작용 423 잠김
```

> **한 계정이 한 분석 안에서 예산을 다 썼다.** 팔로워는 줬는데 팔로잉에서 막혔다. 이건 "다른 유저 요청과 충돌"이 아니라 **"한 건이 계정 하나의 처리량을 넘는다"**는 신호다.

Standard 1건이 요구하는 인증 요청 규모를 보면 놀랍지 않다 — 팔로워 800 + 팔로잉 800(각각 페이지네이션), 후보 프로필, liker 4×150, comment 6×15, 역방향 liker 최대 10×100. **짧은 시간에 한 계정에서 나가기엔 많다.**

**따라서 (B)는 타당하다.** 다만 두 가지 단서가 붙는다.

- **5개가 아니라 2~3개로 시작해도 된다.** 목적이 예산 분할이면 followers/following만 다른 계정에 태워도 계정당 부하가 절반이다
- **관측이 2~3회뿐이다.** 소유자 지적대로 "단일 계정 불가능"도 아직 확정이 아니다. 다만 **확정을 기다릴 이유도 없다** — 분할은 어차피 손해가 없다

## 2. 파이프라인은 아직 안 고쳐졌다

> **질문: 최근 401은 파이프라인을 고친 뒤에 생긴 오류인가?**
> **답: 아니다. 파이프라인은 아직 안 고쳐졌다.**

2026-08-05 이후 `origin/main`의 커밋은 **14개**이고, 전부 익명 preflight와 재고 게이트 관련이다.

```
c82b2c1d  fix: keep anonymous preflight claims valid through retries
bd544b64  fix: allow anonymous exclusion during preflight
01876b76  fix: qualify anonymous preflight dispatch generation
fa81b46f  fix: unblock anonymous preflight creation
1bb8051e  fix: allow anonymous landing preflight handoff (#296)
42ac34ce  fix: use Groble as sole paid inventory source (#293)
...
```

`ANALYSIS_V2_JOB_HANDLER_FAILED`, `ANALYSIS_V2_EVIDENCE_INVALID`, `ANALYSIS_V2_PROFILE_EVIDENCE_INCOMPLETE`를 다룬 커밋은 **없다.**

### 그래서 실패 지점이 둘이고, 순차적이다

```
[수집 단계]  Instagram 401 / rate limit        ← 계정 문제.  최근 E2E가 여기서 죽음
      ↓ (통과하면)
[처리 단계]  evidence / checkpoint 계약 오류    ← 파이프라인 문제. 8/5 14건이 여기서 죽음
```

**8월 5일에는 수집을 통과하고 처리에서 죽었고, 최근에는 수집에서 죽었다.** 둘은 독립적이고 **둘 다 고쳐야 E2E가 나온다.**

- rev.1은 *"파이프라인이 더 문제"*라고 썼는데, 이건 **건수로만 본 것**이다(14 vs 1). 순서로 보면 수집이 먼저다
- 다만 **계정을 5개로 늘려도 8/5의 14건은 그대로 실패한다**는 지적은 유효하다. 파이프라인을 안 고치면 수집을 통과해도 처리에서 죽는다

> **결론: 순서 논쟁이 아니라 병렬 작업이다.** 계정 분할과 파이프라인 수정을 같이 해야 첫 E2E가 나온다. 어느 하나만으로는 안 된다.

## 4. 원가 재추산 — Apify만

### 근거와 한계

문서에 단가가 명시된 것은 `u_profile ≈ $0.0027`(계획값)과 preflight `$0.0026`뿐이다. `u_rel`, `u_liker`, `u_comment`는 **변수로만 있고 측정값이 없다.** 따라서 아래는 **측정된 총액에서 역산한 추정치**이고, 실측으로 대체해야 한다.

**역산 근거 — 2026-07-17 Standard 실패 E2E**

- provider actual `**$2.1816**` (12 runs)
- candidate profile fallback **227건 성공**
- **liker stage 미실행** (upstream 실패)

```
프로필  227 × $0.0027 ≈ $0.61
관계    나머지        ≈ $1.57      ← F+G
```

> ⚠️ 당시 plan 상한이 현재와 다를 수 있어 `u_rel` 단가 자체는 확정하지 않는다. **다만 "관계 목록이 프로필보다 비싸다"는 크기 관계는 유지된다.**

### 소유자 제안 적용 시 (Standard)

당시 제안은 관계 수집 payload를 이용한 전수 성별 분류와 여성 상위 200명의 피드 분석이었다. 현행 결정에서는 1차 입력을 **`profile_pic_url` + `fullname`**으로 좁히고, 80%는 여성 라우팅 점수 상위, 20%는 불확실 후보 탐색에 배정한다. 이 점수는 최종 성별 판정이 아니다.


| 항목              | 현재            | 제안 적용         | 비고                          |
| --------------- | -------------: | -------------: | --------------------------- |
| 관계 목록 (F+G)     | ~$1.57        | **~$1.57**    | **제거 불가. 바닥이다**             |
| 후보 프로필 배치       | ~$1.62 (600건) | **$0**        | `profile_pic_url`이 관계에 딸려 옴 |
| 피드 분석           | —             | ~$0.54 (200건) | 미디어 수집 필요                   |

| **합계**          | **$3.2+**     | **≈ $2.1**    | **약 34% 절감**                |


### 여기서 나오는 결정적 사실

> **관계 목록 `$1.57`만으로도 이미 현재 판매가 1,990원(≈$1.44)을 넘는다.**

소유자 제안은 **두 번째로 큰 항목(후보 프로필 배치)을 없애지만, 1위인 관계 목록은 건드리지 못한다.** 그래서:

- **Apify를 유지하는 한 990/1,990원은 어떤 절감으로도 성립하지 않는다**
- **관계 목록을 selfhosted_auth로 옮기는 것이 유일한 근본 해법**이다. selfhosted_auth의 가치는 바로 여기 있다

### 품질 우려에 대해

1차 라우팅은 **fullname + `profile_pic_url` 이미지**만 사용한다. bio·username·기존 캐시를 전수 조회하지 않는다. 프사가 없거나 판별 근거가 약한 계정은 확정 성별로 만들지 않고 불확실 후보로 남긴다.

상세 수집 상한은 Basic 100명 / Standard 200명이다. 상한의 80%는 여성 라우팅 점수 상위, 20%는 불확실 후보 탐색으로 구성한다. 상한 밖은 `unknown`이 아니라 **`not_screened`**다. 상세 수집 후의 최종 미상 비율은 30% 이하를 품질 SLO로 두되, 숫자를 맞추기 위해 성별을 강제하지 않는다.

## 5. 알리미 모델 — 소유자 설계가 내 반론을 무력화한다

### 내 주장을 철회한다

rev.1은 *"맞팔 변경 빈도를 2주 측정해야 알리미 성립 여부를 안다"*고 했다. **철회한다.**

당시 논의의 핵심은 가치가 없는 달의 사용자 부담을 없애는 것이었다. 현행안은 매월 사후 과금이 아니라 **유료 30일 패스 + 변화가 전혀 없으면 다음 30일 무료 연장**이다.


| rev.1의 반론          | 소유자 모델의 답                         |
| ------------------ | --------------------------------- |
| 변경이 월 0회면 구독 가치가 0 | 다음 30일을 무료 연장해 사용자 손해를 완충한다 |
| 그러면 매출이 안 난다 | 설정비는 최초 스냅샷 원가를 부담하고, 무변화 연장은 저비용 count 감시만 수행한다 |


**가치 발생 시에만 과금하는 구조라 빈도가 낮아도 서비스가 성립한다.** 소유자 말이 맞다. 빈도는 **매출 규모 예측**에는 여전히 필요하지만 **착수 전 필수 조건이 아니다.**

### 모델 요약

```
가입 설정비     →  전체 팔로워/팔로잉 기준 스냅샷 (1회)
매일          →  팔로워/팔로잉 "수"만 비인증 트래킹     ← 원가 거의 0, 계정 리스크 0
변화 감지     →  전체 재수집 → 새 계정 추출 → 프로필·피드 분석 → 알림톡
30일 감시비    →  Light 1,990원 / Standard 2,990원, 내부 refresh 원가 상한 적용
```

### 이 모델이 판독기보다 나은 점


|              | 내용                                                    |
| ------------ | ----------------------------------------------------- |
| **인증 의존**    | 매일 조회는 **비인증**. 계정이 죽어도 감지는 계속된다                      |
| **실패 성격**    | 백그라운드라 실패가 **환불이 아니라 내일 재시도**                         |
| **DM 상한**    | "새 맞팔 3개 생김"은 판정이 아니라 **사실**. *"뭘 보고 판단하냐"*가 성립하지 않는다 |
| **원가·과금 정합** | 변화 없는 달은 원가도 매출도 0                                    |


### 기술적으로 짚을 것 두 가지

**① "수"만 보면 순변화 0을 놓친다.** 1명 언팔 + 1명 팔로우 = 수 동일. 흔한 케이스다.

- 소유자 표현이 *"팔로워/팔로잉 **모두** 변화가 있는 날"*이었는데, **AND면 더 많이 놓친다. OR이어야 한다**
- 순변화 0을 잡으려면 **주기적 강제 재수집**(예: 주 1회)이 필요하다. 그 빈도가 원가를 결정한다
- 다만 **완벽하지 않아도 되는 서비스다.** 이번에 놓쳐도 다음 변화 때 잡힌다

**② 비인증 매일 조회의 rate limit.** 7월 canary에서 Cloud Run egress의 비로그인 프로필 요청이 대규모 `429`를 받아 selfhosted 성공 0건이 난 이력이 있다. 유저당 하루 1회라 판독기의 대량 조회와는 규모가 다르지만, **유저가 늘면 같은 벽을 만난다.** 전역 pacing이 이미 있으니 그 위에서 설계한다.

| ① Apify + 9,900원    | 원가 절감 없이 가격만 올림                                     | **불필요.** 절감하면 4,900원에서 마진이 난다         |
| ② selfhosted 계정 풀   | 요청 예산 분할 (B 용도)                                     | **타당.** 단 파이프라인 수정과 **병렬**로. 2~3개로 시작 |
| ③ 알리미               | 구독 전환                                               | **채택 가치 있음.** 단 판독기의 후속이지 대체가 아니다     |
| **④ 원가 절감 + 중간 가격** | 소유자 제안 + Basic 2,900 / Standard 4,900, **Apify 유지** | **가장 빨리 매출이 나는 길**                    |


### ④가 새로 보이는 이유

- 87일간 GCP가 0이라 **Apify만 감당하면 된다**
- 소유자 제안으로 Apify가 약 34% 줄어든다
- 그 원가($2.1)에서 **4,900원이면 마진 35%**
- **selfhosted_auth를 기다리지 않고 지금 팔 수 있다**

그리고 ④는 ②·③을 배제하지 않는다. **87일 안에 selfhosted_auth가 관계 목록을 커버하면 그때 가격을 내리거나 마진을 키우면 되고, 알리미는 그 위에 얹는다.**

## 7. 당시 권고와 현재 판정

### 2026-08-07 당시 권고 (역사적 기록)

1. **원가 절감안 구현** — 후보 프로필 배치 제거(`profile_pic_url` 재사용), 전수 성별 분류(Gemini 무료), 피드 분석 Basic 100 / Standard 200 제한, liker·comment는 원가 확인 후 결정
2. **가격 재설정** — Basic **2,900원** / Standard **4,900원** 검토. 990/1,990은 어떤 절감으로도 성립하지 않는다
3. **파이프라인 계약 오류 수정** — `JOB_HANDLER_FAILED`, `EVIDENCE_INVALID`, `PROFILE_EVIDENCE_INCOMPLETE`. **아직 손대지 않았다**
4. **계정 2~3개로 요청 예산 분할** — followers/following을 서로 다른 계정에. 5개는 나중에
5. **로그인 이전 배포** — 가격을 보는 사람을 18명에서 세 자리로

### 87일 크레딧 만료 전에

- selfhosted_auth가 **관계 목록**을 안정적으로 커버하는지 판정. 그게 되면 Apify 바닥이 사라진다
- Gemini 실제 사용량 측정 — 크레딧이 끝나면 다시 지배 항목이 된다
- 알리미 착수 여부 결정

### 하지 않을 것

- **Apify 복귀 + 9,900원** — 절감하면 그 가격이 필요 없다
- **5계정 즉시 구축** — 2~3개로 예산 분할 효과를 먼저 확인
- **판독기 보류** — 알리미는 판독기의 후속이지 대체가 아니다. 온보딩이 없으면 알리미의 첫 경험이 빈다

## 8. 현재 한 문장

> 첫 실결제로 990원의 지불 행동이 확인됐으므로 판독기는 Apify 제한 판매를 유지한다. 동시에 Basic/Standard E2E와 원가를 복구하고 맞팔 알리미 30일 유료 파일럿을 병행한다. 2,900원 / 4,900원은 즉시 적용 가격이 아니라 정상 전달과 원가가 쌓인 뒤의 후속 실험이며, selfhosted_auth는 별도 canary가 통과하기 전까지 운영 경로가 아니다.
